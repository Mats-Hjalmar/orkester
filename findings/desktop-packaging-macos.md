# Desktop packaging (macOS, electron-builder)

- 2026-08-13: Packaging the Electron desktop with **electron-builder 26.15.3** (config in `desktop/electron-builder.yml`, run via root `pnpm desktop:dist`). Target is a single **universal** dmg (`arch: [universal]`) — electron-builder packages x64 and arm64 separately into `release/mac-universal-{x64,arm64}-temp` and lipos them via `@electron/universal`. Works with zero extra config here because the app has **no native modules**, so both arch bundles carry byte-identical JS and only the Electron binaries differ.
- 2026-08-13: **The workspace dep is the whole packaging problem.** `@orkester/core` is a `workspace:*` dep, and `externalizeDepsPlugin` left `require('@orkester/core')` in `out/main/index.js` — unresolvable next to a packaged app, and electron-builder's pnpm dependency collector would have had to dereference the `node_modules/@orkester/core` → `packages/core` symlink and copy the whole package (src, tests, its own node_modules). Fix: inline core into the main bundle with `main.build.externalizeDeps.exclude: ['@orkester/core']`. electron-vite externalizes `electron` + every `node:*` builtin **unconditionally** (`lib-*.js` sets `external: ['electron', /^electron\/.+/, ...builtinModules…]`), so excluding core from externalization does NOT drag node builtins into the bundle — the RN/Node boundary is untouched. Confirmed: main's only remaining `require()`s are `electron`, `dgram`, `fs`, `http`, `https`, `os`, `path`. Builder log then reports "no node modules returned while searching directories" and `files:` needs only `out/**` + `package.json`.
- 2026-08-13: `externalizeDepsPlugin` is **deprecated in electron-vite 5** — use the `build.externalizeDeps` config option instead (the auto-injected plugin is skipped if a user plugin named `vite:externalize-deps` is present, so don't mix the two). `exclude` matching handles subpath imports: the plugin builds `external: [...deps, /^(dep1|dep2)/.+/]`, so excluding `@orkester/core` also inlines `@orkester/core/state` and `@orkester/core/node`.
- 2026-08-13: electron-builder **refuses a semver range** for electron: `Electron version "^33.2.0" is a range, not a fixed version`. It downloads per-arch binaries and needs an exact release. Pinned `"electron": "33.4.11"` in `desktop/package.json`. Alternative is `electronVersion` in the builder config, but pinning keeps one source of truth.
- 2026-08-13: `CSC_NAME` / `mac.identity` must be the identity **without** the type prefix — `Isotop AB (3GN395FUH4)`, not `Developer ID Application: Isotop AB (3GN395FUH4)`. The full string fails with "Please remove prefix … appropriate certificate will be chosen automatically".
- 2026-08-13: Signed with hardened runtime (`codesign -dv` shows `flags=0x10000(runtime)`) + a secure timestamp. Not sandboxed, so **no** network entitlements are needed for SSDP.
- 2026-08-13: **`com.apple.security.cs.allow-jit` is the only entitlement Electron 12+ needs**, and `build/entitlements.mac.{plist,inherit.plist}` grant exactly that — verified by launching the packaged app (window up in ~2s, clean stdout). electron-builder's default template (`app-builder-lib/templates/entitlements.mac.plist`, untouched since Jan 2020) is **over-broad**: it also grants `allow-unsigned-executable-memory`, `allow-dyld-environment-variables` and `disable-library-validation`. Per [@electron/notarize](https://github.com/electron/notarize#prerequisites), `allow-unsigned-executable-memory` "should not be applied" on Electron 12+ as it increases attack surface (fixed by electron#26331); `allow-dyld-environment-variables` was deleted from electron-builder's own template in 2019 as a code-injection vector; `disable-library-validation` is unnecessary because electron-builder re-signs every nested Mach-O with the same Team ID, and Gatekeeper runs *extra* checks on apps that set it. Same file is used for `entitlementsInherit`, so the four Helper `.app`s (separate executables — they do not inherit from the host) get the same single entitlement. Don't add to this file without a reproduced failure.
- 2026-08-13: **Config-shape trap for future upgrades:** electron.build's live docs show `mac.sign.*`, which is electron-builder **27.0.0-alpha** shape and silently does nothing on 26.x. On 26.x the keys are flat: `mac.entitlements`, `mac.entitlementsInherit`, `mac.hardenedRuntime` (defaults to `true` on darwin). Same trap for notarization: on 26.x `mac.notarize` is typed `boolean` — the object form (`notarize: {teamId: …}`) is v27's and is **silently ignored**, with the team taken from the environment regardless. Credentials come from env only: `APPLE_KEYCHAIN` + `APPLE_KEYCHAIN_PROFILE`, or `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`. Note `notarize: true` with no credentials present **fails the build**, so leaving it enabled speculatively breaks `pnpm desktop:dist` for anyone without them.
- 2026-08-13: electron-builder injects **placeholder** `NSCameraUsageDescription` / `NSMicrophoneUsageDescription` ("This app needs access to the camera") into every mac Info.plist. Orkester uses neither; removed by setting them to `null` in `mac.extendInfo`.
- 2026-08-13: SSDP discovery is UDP multicast on the LAN, and per [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) that needs the **Local Network** privilege on macOS 15+ regardless of sandboxing — sending a UDP multicast *and* receiving an incoming one both require it (receiving a UDP *unicast* does not, so `M-SEARCH` replies would arrive but `NOTIFY` announcements would not). Checks live "deep in the networking stack", so `node:dgram` is not a loophole. `mac.extendInfo.NSLocalNetworkUsageDescription` supplies the prompt text (missing ⇒ generic Apple text, not a hard failure; must be in Info.plist proper, not InfoPlist.strings). `NSBonjourServices: [_sonos._tcp]` is set as cheap insurance even though `discoveryTransport.ts` uses raw `node:dgram` to 239.255.255.250:1900 and never touches Bonjour — whether macOS enforces the list for non-Bonjour APIs is undocumented, and a silent discovery failure on someone else's Mac is not remotely debuggable. Two operational notes: **there is no supported way to reset this permission on macOS** (it's a Network Extension packet filter, not TCC — `tccutil` does nothing), and the alert is not shown at all for very short-lived processes, so don't exit on the first discovery failure.
- 2026-08-13: **Local Network grants can leak between unrelated Electron apps.** TN3179: the permission is keyed on the main executable's Mach-O `LC_UUID`, not the bundle ID — and every electron-builder app built from the same prebuilt Electron binary shares one UUID. Filed as [electron-builder#9158](https://github.com/electron-userland/electron-builder/issues/9158), **closed won't-fix**; the only fix is linking with `-random_uuid`, i.e. building Electron from source. So a user who already denied Local Network to some other Electron 33 app may see that decision applied to Orkester. Worst case, a *missing* UUID makes Settings show the permission as granted while access is silently denied (`nehelper … failed to get UUIDs for` in the log).
- 2026-08-13: **Unnotarized is not the same as unsigned, but Gatekeeper still blocks it.** `spctl --assess --type execute` on the signed app: `rejected  source=Unnotarized Developer ID`, even though `codesign --verify --deep --strict` says "valid on disk / satisfies its Designated Requirement". **Control-click → Open no longer works** — Apple removed that override in macOS 15 Sequoia ([Developer News 2024-08-06](https://developer.apple.com/news/?id=saqachfa)), and macOS 26 is the same. The dialog offers only "Move to Trash" / "Done"; the sole route is System Settings → Privacy & Security → **Open Anyway** + login password, and that button expires ~1h after the launch attempt. Also dead: `spctl --add`/`--enable`/`--disable`. Recipient instructions live in `desktop/release/FIRST-RUN.txt`, which deliberately warns *against* `xattr -cr` — that strips `com.apple.cs.CodeDirectory`/`CodeSignature` xattrs where signatures for non-Mach-O bundle files live, leaving "is damaged and can't be opened" (`xattr -dr com.apple.quarantine` is the safe form, but macOS 26.4 now blocks suspicious Terminal pastes anyway). Keeping the real Developer ID signature is what makes this a *warnable* block rather than a dead end; notarizing removes it entirely.
- 2026-08-13: Smoke test for a packaged build — run `release/mac-universal/Orkester.app/Contents/MacOS/Orkester` **directly** and watch stdout. main/index.ts already forwards renderer console + `did-fail-load` + `preload-error` to the terminal, so a broken bundle (e.g. an unresolved `@orkester/core`) shows up immediately instead of as a blank window. Verify the window really came up with `osascript -e 'tell application "System Events" to tell process "Orkester" to get count of windows'`. Sizes: 418M .app, 173M dmg (universal doubles the Electron binaries).
