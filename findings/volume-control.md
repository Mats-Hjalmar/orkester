# Volume control

- 2026-06-30: "Volume maxing sometimes" — hardware volume is ONLY ever written by `api.setVolume`, whose sole caller is `setVolForRooms` (store.tsx), reached only from a `TrackBar` `onScrub` (a tap/drag on a volume bar). Nothing on launch, connect, play, seek, or reconcile writes volume; `optimistic()` does a single dispatch+call with no replay queue. So a "max" can only come from a touch computing `x/w ≈ 1`.
- 2026-06-30: Root cause was the **fabricated fallback**. `groupVol` returned `?? 33` (earlier `|| 0`) for rooms with no real reading yet, and the slider stayed interactive. Dragging a slider whose position is a *guess* writes an absolute volume from where you tapped relative to that fake baseline → can jump to max.
- 2026-06-30: Fix — `groupVol(g)` now returns `number | null`: null unless EVERY member room has a real reading (`state.roomVol[r] !== undefined`; a genuine 0 stays 0). All four volume bars (RoomGroupCard, Speakers, mobile + desktop NowPlaying) render only when `groupVol !== null`; otherwise the control is hidden, not guessed. Removed `DEFAULT_ROOM_VOLUME`. `state.roomVol` is `{}` at launch, so the bar appears only after the 2.5s volume poll / `refreshGroup` snapshot fills in real values.
- 2026-08-17: Mute "did nothing" in the desktop app. Same class of bug as the volume one, mirrored: the UI read `Group.muted`, but the only writer of that field was the `groupSnapshot` action (`focusGroup`/manual refresh). Both mute writers — `setRoomMuteOptimistic` and the 2.5s poll's `roomMute` — wrote only `state.roomMute`, a slice no component read. So a click never changed the icon, and because `toggleMute` computed `next = !g.muted` off that frozen field it re-sent `SetMute 1` forever: **unmute was unreachable from the UI**.
- 2026-08-17: Fix — deleted `Group.muted` and derived mute from `state.roomMute` via `mutedOf(state, group)` (exported from `state/reducer.ts` beside `activeOf`), exposed as `store.groupMuted(g): boolean | null`. Same honesty rule as `groupVol`: null unless EVERY member room has a real reading, so mute is never guessed as `false`. The rule generalises — **a field the UI reads must be written by every path that changes it; if two writers exist, derive it from the slice they share rather than storing a copy.**
- 2026-08-17: Two secondary mute bugs fixed alongside. (1) Mute shared the `transport:<gid>` single-flight slot with play/pause/next/prev/seek, so a mute click during ANY in-flight transport op was silently dropped — it now has its own `mute:<gid>` slot (different service: RenderingControl, not AVTransport) plus `store.mutePending(gid)` for the spinner. (2) `optimistic()` swallowed the rejection after reverting, so a UPnP fault on `SetMute` never reached `singleFlight`'s `onError` and the control just looked inert; it now rethrows after reconciling.
- 2026-08-17: Mute writes now stamp `lastVolWriteAt` too. `pollVolumes` reads volume AND mute together and skips a room inside `VOLUME_QUIET_MS`, so without the stamp a poll landing mid-write could undo the optimistic toggle.
